# Участие в разработке OSTP

Код, сообщения об ошибках, тесты, документация и проверка безопасности приветствуются. Присылая изменения, вы соглашаетесь, что они распространяются под лицензией проекта (AGPL-3.0).

---

## Подготовка окружения

Понадобятся:

*   **Rust** (актуальная стабильная версия): через [rustup](https://rustup.rs/).
*   **Git**.
*   Только для десктопного GUI: **Node.js 18+** и [зависимости Tauri](https://tauri.app/start/prerequisites/).
*   Только для Android-приложения: **Flutter** и Android NDK.

### Сборки и тесты идут на GitHub Actions

Проект большой, поэтому тесты и сборки выпусков не запускают на машине разработчика. Для этого есть
[`.github/workflows/ci.yml`](.github/workflows/ci.yml):

*   Сам он запускается при пуше в `beta` и `master`, если менялся код. Изменения только в `docs/`, файлах Markdown и лицензиях ничего не запускают.
*   Для `alpha` и любой другой ветки запускайте вручную: вкладка Actions (*Run workflow*) или `gh workflow run ci.yml --ref alpha`.
*   Он гоняет тесты ядра, клиента, сервера, CLI, SSH и JNI (в том числе сквозные тесты v6 и роуминга), собирает бинарники для Linux и Windows,
    которые остаются артефактами запуска (`gh run download <id> --name ostp-linux-amd64`), и проверяет приложения (статические проверки и их тесты).
*   Результаты: `gh run list --workflow ci.yml`, `gh run view <id> --log-failed`.

Пакеты выпуска (установщики, APK, `ostp` для всех платформ) собирает `.github/workflows/release.yml` по тегу, не вручную.

Для быстрой проверки своего изменения можно запустить `cargo check -p <крейт>` или `cargo test -p <крейт>` для затронутого крейта.
Веб-панель (`ostp-server/panel/`) — обычные HTML/CSS/JS, встроенные в бинарник сервера: отдельной сборки у неё нет.

### Выпуски

Выпуски делает мейнтейнер через `scripts/gha.ps1`; больше никто не ставит теги и не переводит ветки. У цикла одна целевая версия (сейчас 0.5.0), она
остаётся в манифестах на всех предварительных выпусках; двигается только счётчик канала, и он живёт в теге (`v0.5.0-alpha.6`, `v0.5.0-beta.1`, затем `v0.5.0`).
Файл `.release-state.json` в корне репозитория помнит целевую версию, канал и оба счётчика; `gha.ps1` обновляет его, а пуш тега запускает
`release.yml`. Перевод в `beta` и `master` — это fast-forward от ветки ниже. Не правьте `.release-state.json` вручную и не пушьте теги `v*`.

## Структура проекта

Cargo-workspace (`Cargo.toml`) состоит из таких участников:

| Путь | Что это |
|---|---|
| [`ostp/`](ostp) | Бинарник `ostp`: CLI, мастер настройки, команды `cert`/`sub`/`panel`/`dns`/`overnet`/`warp`/`key`/`manage`/`log`, запуск клиента или сервера по конфигу. |
| [`ostp-core/`](ostp-core) | Протокол: рукопожатие Noise (v5 и v6), обфускация заголовков, кадры и паддинг, сессионный слой, ARQ, контроль перегрузки, сообщения реле, ссылки, приватность логов. |
| [`ostp-client/`](ostp-client) | Клиент: локальный SOCKS5/HTTP-прокси, режим TUN, исключения, носители UDP/UoT/TLS, роуминг сессии, MTU пути, пробер сети. |
| [`ostp-server/`](ostp-server) | Сервер: диспетчер сессий, выход в интернет, разбор TCP (UoT, TLS, HTTP upgrade, приманка), сертификаты, подписки, веб-панель и API. |
| [`ostp-ssh/`](ostp-ssh) | SSH-клиент, которым приложения ставят и настраивают сервер, и хранилище сохранённых серверов. |

| [`ostp-tun/`](ostp-tun) | TUN-устройство и маршруты для каждой платформы (Wintun на Windows). |
| [`ostp-warp/`](ostp-warp) | Cloudflare WARP как выход сервера: WireGuard и SOCKS5-прокси в пользовательском пространстве. |
| [`ostpd/`](ostpd) | Привилегированный помощник, который держит туннель для десктопного GUI на Windows. |
| [`ostp-jni/`](ostp-jni) | JNI-обвязка для Android-приложения. |
| [`third_party/netstack-smoltcp/`](third_party/netstack-smoltcp) | Пропатченная копия `netstack-smoltcp` (поддержка TCP reset), см. её README. |

Вне workspace:

| Путь | Что это |
|---|---|

| [`ostp-flutter/`](ostp-flutter) | Android-клиент (Flutter). |

| [`scripts/`](scripts) | `install.sh`, `install.ps1`, `gha.ps1` (выпуски), `build.ps1` (локальные пакеты). |

## Стратегия веток

В репозитории три долгоживущие ветки, по возрастанию стабильности:

| Ветка | Роль |
|---|---|
| `alpha` | Активная разработка. Вся новая работа и фиксы попадают сюда первыми (в том числе работа над 0.5.0; протокол v6 уже в `alpha`). |
| `beta` | Перематывается вперёд (fast-forward) от `alpha`, когда та немного «отлежалась». Собирается в канал выпусков `{версия}-beta.N`. |
| `master` | Перематывается вперёд от `beta`, когда та доказала стабильность. Стабильные выпуски (`vX.Y.Z`) режутся отсюда. |

В `beta` и `master` **никогда** не коммитят напрямую - они только перематываются вперёд от ветки уровнем ниже. Это значит, что промоушен - всегда обычный `git merge` без единого конфликта по построению: не мержите/не ребейзьте свою фичу прямо в `beta` или `master`.

**PR от контрибьюторов нацелены на `alpha`**, не на `master`.

## Процесс разработки

1.  **Проверьте существующие задачи** или откройте новую тему (Issue) для обсуждения предлагаемых изменений.
2.  **Сделайте fork репозитория** и создайте новую ветку от `alpha`:
    ```bash
    git checkout alpha
    git checkout -b feat/имя-вашей-фичи
    ```
3.  **Внесите необходимые изменения** и добавьте соответствующие модульные или интеграционные тесты.
4.  **Отформатируйте изменённые файлы** через `rustfmt`. Дерево пока
    отформатировано не полностью, поэтому не запускайте `cargo fmt --all` в
    ветке с фичей: ваше изменение утонет в постороннем переформатировании.
5.  **Запустите clippy** и не добавляйте новых предупреждений:
    ```bash
    cargo clippy --workspace --all-targets
    ```
6.  **Запустите тесты** затронутых крейтов (`cargo test -p <крейт>`) и отправьте ветку; полный набор идёт на GitHub Actions (см. выше).
7.  **Добавьте строку в [`CHANGELOG.ru.md`](CHANGELOG.ru.md) и [`CHANGELOG.md`](CHANGELOG.md)** в раздел *Не выпущено* для всего, что заметит пользователь. Каждое изменение попадает в оба файла.
    Документы в `docs/` есть на английском и русском с одинаковым содержанием: меняйте оба.

## Оформление коммитов

```
<тип>(<область>): <краткое описание в повелительном наклонении>

<опционально: тело - объясняет ПОЧЕМУ, а не что; диф и так показывает что изменилось>
```

- **Тип** - один из: `feat` (новая функциональность), `fix` (исправление бага), `docs`, `refactor` (без изменения поведения), `perf`, `test`, `chore` (зависимости/тулинг/версии), `ci`, `security`.
- **Область** (опционально) - крейт или часть проекта: `client`, `server`, `core`, `gui`, `flutter`, `ci`, `docs` и т.д., например `fix(client): ...`.
- **Краткое описание** - повелительное наклонение ("добавь", а не "добавил"/"добавляет"), без точки в конце, желательно до ~70 символов.
- **Тело** - только когда причина не очевидна из дифа: какой баг это чинит, какое ограничение определило подход, на какой trade-off вы пошли. Не пересказывайте то, что и так видно в дифе. Перенос строк на ~72 символах.

```
fix(server): отбрасывать junk-фреймы по маркеру для каждого ключа, а не глобальному

Фиксированный 4-байтовый маркер на каждом junk-пакете сам по себе - сигнатура
DPI, по которой можно фильтровать любого наблюдателя во всех деплойментах OSTP
сразу. Выводим маркер из access_key (HKDF, та же схема что у
obfuscation_key/psk), чтобы он был индивидуальным для ключа и неотличимым от
случайной полезной нагрузки пакета.
```

Несколько несвязанных изменений - это несколько отдельных коммитов, а не один сборный. Это сохраняет пользу от `git bisect` и код-ревью. Squash-merge подходит для PR с парой коммитов вроде "fix typo" / "address review", но не сквошьте вместе логически разные изменения.

## Правила оформления кода

*   **Безопасность (Safety)**: Избегайте использования блоков `unsafe` везде, где это возможно. Допускается их использование только для низкоуровневых системных вызовов (например, FFI-настройки сокетов `setsockopt`). Любой блок `unsafe` должен сопровождаться комментарием `// SAFETY: ...`.
*   **Документация**: Пишите документацию для публичных модулей, структур и методов. Сохраняйте целостность комментариев при рефакторинге.
*   **Логирование**: Используйте фреймворк `tracing` для структурированного логирования. Не используйте `println!` в рабочем коде.
*   **Интерфейс**: В GUI и панели держитесь существующего вида. Без эмодзи, градиентов и декоративных эффектов; вёрстка должна работать на экране телефона.

## Создание Pull Request

1.  Отправьте ветку в ваш fork-репозиторий:
    ```bash
    git push origin feat/имя-вашей-фичи
    ```
2.  Создайте Pull Request (PR) в ветку `alpha` основного репозитория (см. [Стратегия веток](#стратегия-веток) - `master` получает только fast-forward от `beta`, PR туда не принимаются напрямую).
3.  Подробно опишите внесенные изменения: какая проблема решается, как проводилось тестирование и на каких платформах проверялась сборка.
4.  CI сам не запускается на ветке, которая не `beta` и не `master`: запустите `ci.yml` на ней вручную (или это сделает мейнтейнер) и убедитесь, что он прошёл.
