# Интеграции

`ostp-core` сам ничего не вводит и не выводит. Каждое приложение подключает его и предоставляет сокеты, TUN-адаптер и интерфейс, как описано ниже.

## Android: приложение на Flutter и JNI
`ostp-flutter` — мобильное приложение (Flutter; пока только Android). На Android оно встраивает Rust-движок клиента через `ostp-jni`, отдельный крейт с небольшой JNI-поверхностью (`Java_net_ostp_client_OstpClientSdk_*`), которую использует Kotlin-слой приложения (`OstpClientSdk.kt`, `OstpVpnService.kt`, `MainActivity.kt`): старт/стоп клиента, метрики, логи, смена сети, пробер, подписки, проверка обновлений и `serversCall` для управления сервером (ниже).

- **Среда выполнения**: `ostp-jni` запускает собственные многопоточные среды Tokio в процессе приложения, а Kotlin вызывает её из фоновых потоков, так что сетевой ввод-вывод туннеля не блокирует UI-поток.
- **Опрос**: метрики, логи и вывод команд сервера читаются обычными геттерами; push-канала нет.
- **Раздельное туннелирование** — по приложениям (списки разрешённых/исключённых приложений `VpnService`); исключений по имени процесса на Android нет.

## Десктопный GUI
`ostp-gui` — десктопное приложение на Tauri v2 (Windows и Linux), которое запускает тот же клиентский движок в своём процессе в режиме прокси и через вспомогательный процесс в режиме TUN. Тема одна, тёмная; в верхней панели две кнопки: пробер сети и настройки.

### Права для TUN
Создание TUN-адаптера требует повышенных прав, а само приложение с ними работать не должно. Поэтому TUN настраивает `ostpd` — небольшой процесс, который приложение запускает и которым управляет по локальному командному каналу (старт и стоп, с конфигом и токеном). Повышенные права нужны только хелперу (UAC в Windows, polkit/pkexec в Linux). Собственно код создания адаптера лежит в общем крейте `ostp-tun`, который используют и хелпер, и нативный TUN-путь CLI (см. [`client.md`](client.md)).

### Обновления
При запуске (это можно отключить в настройках) и по кнопке «Check for updates now» приложение проверяет, нет ли на GitHub более новой стабильной или бета-версии. Оно только сообщает об этом; ничего не скачивается, пока пользователь не нажмёт «Update now». Тогда приложение скачивает свою сборку из релиза, сверяет её с SHA-256, который GitHub публикует для каждого файла релиза (хэша нет или он другой: ничего не устанавливается), останавливает туннель и устанавливает её:

- Windows, установка через setup: новый установщик запускается как обновление (`/P /R /UPDATE`: полоса прогресса без вопросов, ярлыки и данные сохраняются, приложение перезапускается). Windows один раз спрашивает согласие, потому что приложение установлено для всех пользователей.
- Портативная версия для Windows, Linux и macOS: файлы рядом с приложением (`ostp-gui`, `ostpd`, `wintun.dll`) заменяются, и приложение перезапускается. Старые файлы сначала переименовываются в `.old`, возвращаются на место, если что-то пошло не так, и удаляются при следующем запуске. Папка должна быть доступна пользователю на запись.

Если установить не удалось, окно показывает причину и предлагает страницу релиза.

### Серверы с фильтрацией DNS
Ссылка или подписка содержит `owndns=true`, когда сервер держит собственный резолвер (10.1.0.1), и `dnsall=true`, когда оператор отвечает на каждый DNS-запрос независимо от того, какому резолверу он адресован, и отказывает зашифрованному DNS (DoT, DoH). Оба приложения хранят эти флаги в профиле и записывают их обратно, когда профилем делятся.

При первом подключении к такому профилю, до запуска туннеля, приложение показывает уведомление: резолвер оператора фильтрует доменные имена по спискам блокировки и видит, какие имена вы запрашиваете (при `dnsall` ещё и то, что публичный DNS на этом сервере ничего не меняет). Три кнопки неактивны первые 5 секунд, закрыть уведомление можно только выбором:

- *Use the operator's DNS*: DNS для этого профиля 10.1.0.1.
- *Use a public DNS*: собственная настройка DNS приложения, если она задана, иначе 1.1.1.1.
- *Keep my settings*: ничего не меняется, действует настройка DNS приложения.

Выбор хранится в профиле (переживает перезапуск и обновление подписки) и повторно не спрашивается. Его можно изменить в редакторе профиля, поле *DNS of this server*: *Ask on the next connection*, *Operator's DNS*, *Public DNS*, *My settings*. Профили без этих флагов не затрагиваются.

Приложение для Android делает то же со своим APK: скачивает сборку для архитектуры телефона, проверяет размер и SHA-256 и открывает системный установщик, который ставит её поверх текущего приложения, потому что обе подписаны одним ключом. Если приложению ещё не разрешено устанавливать приложения, оно сначала открывает эту настройку.

### Подписки с лимитом устройств
Сервер может задать пользователю `max_devices` (см. [tls.md](tls.md), *Лимит устройств*) и считать устройства, которые загружают его подписку. Для этого приложение должно прислать идентификатор устройства. В обоих приложениях для этого есть переключатель в настройках, *Send a device ID to subscriptions* (Android: *More settings*; десктоп: *More settings*, *Application*), и по умолчанию он **выключен**. Пока он выключен, о устройстве не отправляется ничего.

Когда он включён, запрос подписки несёт три заголовка: `x-hwid`, `x-device-os` (например `Windows 11` или `Android 14`) и `x-device-model` (архитектура процессора на десктопе, модель телефона на Android; имя компьютера никогда). Идентификатор — `hex(HMAC-SHA256(ключ = идентификатор машины в системе, сообщение = "ostp-hwid:" + хост сервера))`, обрезанный до 32 символов. Он делается для каждого сервера отдельно, поэтому два сервера не могут понять, что за двумя идентификаторами один человек, а сам идентификатор машины (`MachineGuid`, `IOPlatformUUID`, `/etc/machine-id`, `ANDROID_ID`) устройство не покидает. Идентификатор переживает переустановку приложения, и по этому сервер узнаёт устройство снова. Он отправляется только при загрузке подписки, не вместе с трафиком туннеля.

Два ответа сервера обрабатываются отдельно:

- *Подписке нужен идентификатор устройства* (`hwid_required`): после загрузки, которую начали вы (добавление подписки, кнопка обновления), появляется диалог «This subscription limits devices. The server needs this device's ID to count it. Send it?»; *Send and retry* включает переключатель и пробует ещё раз, *Cancel* оставляет его выключенным. Фоновое обновление никогда не спрашивает: на карточке подписки написано `Device ID needed: turn on "Send a device ID to subscriptions" in settings`.
- *Лимит достигнут* (`device_limit`): сообщение самого сервера показывается на карточке подписки и во всплывающем сообщении. Освободить место может владелец сервера, удалив устройство в панели.

CLI отправляет идентификатор только при `"send_hwid": true` в конфигурации (см. [client.md](client.md)).

## Свой сервер из приложений

Оба приложения умеют поставить OSTP на VPS и потом управлять им — для тех, кто купил сервер и не хочет разбираться в Linux. Работу по SSH делает крейт `ostp-ssh`, общий для десктопа (команды Tauri в `ostp-gui/src-tauri/src/servers.rs`) и Android (`serversCall` в `ostp-jni`).

**Первый запуск.** Если в приложении нет ни профилей, ни подписок, оно открывается на экране *Let's get started*:
- *I have a link*: ссылка `ostp://` или URL подписки (на Android — ещё и по QR-коду).
- *I have a server*: адрес, SSH-порт, логин и пароль или приватный ключ (OpenSSH, PEM или PuTTY `.ppk`, с парольной фразой). Приложение подключается, проверяет систему (архитектура, systemd, root или sudo), скачивает скрипт установки своего канала выпуска (`master`, `beta` или `alpha`) и запускает `install.sh -y`: он ставит OSTP, пишет конфиг с одним пользователем и запускает службу. Ссылки первого пользователя становятся профилями в приложении. Каждый шаг и вывод сервера видны по ходу.

**Управление сервером** (*Settings → Server management*), для каждого сервера:
- *Status*: состояние службы, версия, время работы, подключённые сеансы, пользователи, ОС, нагрузка, память, диск; перезапуск и обновление OSTP.
- *Users*: добавить, переименовать, отозвать; трафик (сохраняется при перезапуске и обновлении) и кто в сети; добавить ссылки пользователя в это приложение; QR-код.
- *Connection*: порт UDP/TCP, TLS на 443 с доменом и сроком сертификата, выпуск сертификата (`ostp cert issue`), подписки вкл/выкл.
- *DNS*: DNS-фильтр сервера (списки блокировки, безопасный поиск), состояние берётся из `ostp manage dns`. Переключатели фильтра, перехвата (сервер отвечает на каждый DNS-запрос своих клиентов, какому бы резолверу он ни был адресован; по умолчанию он отвечает только на запросы к своему адресу, 10.1.0.1), блокировки шифрованного DNS (DoT/DoH; действует только при включённом перехвате) и безопасного поиска, а также *Update lists*. Резолверы верхнего уровня, списки с их состоянием и число подмен и собственных правил показаны только для чтения (менять их в веб-панели). Каждое изменение сначала спрашивает подтверждение: служба перезапускается, подключённые клиенты на несколько секунд отключаются. Если OSTP на сервере слишком старый для `manage dns`, приложение так и говорит и больше ничего не предлагает.
- *Management*: веб-панель (включить со входом, открыть, выключить), лог сервера, SSH-ключ хоста, переименовать, перезагрузить, удалить OSTP, забыть сервер.

Изменения, которые перезапускают службу, не выполняются, пока VPN этого устройства идёт через тот же сервер: ответ бы не пришёл.

**Как приложение общается с сервером.** Всё идёт по одному SSH-соединению на сервер, открытому, пока работает приложение. Команды выполняются от root: напрямую при входе как root, иначе через `sudo -S` с паролем входа на stdin, так что он не появляется в командной строке. Состояние и изменения идут через `ostp manage` (JSON, см. [`server.md`](server.md)); длинные операции (установка, обновление, сертификат) передают вывод построчно.

**Веб-панель.** Приложение пробрасывает локальный порт на `127.0.0.1` к порту панели на loopback сервера через SSH-соединение и открывает её в браузере (на Android — во встроенной вкладке браузера, так что приложение остаётся на переднем плане и проброс жив). Открывать порт на сервере не нужно. Ещё приложение показывает адрес панели через VPN, `http://10.1.0.1:<порт>/<webpath>/`: он открывается в любом браузере на устройстве, подключённом через этот сервер.

**Безопасность.**
- Ключ хоста SSH запоминается по отпечатку SHA-256 при первом подключении; другой ключ потом отвергается («host key changed»), а не принимается молча.
- Пароль или ключ сохраняется, только если пользователь попросил. Он запечатывается ChaCha20-Poly1305 в `servers.json` под случайным 32-байтным мастер-ключом, а мастер-ключ лежит в системном хранилище (Windows Credential Manager, Secret Service на Linux; на Android его оборачивает Android Keystore). Без рабочего хранилища секреты не записываются, и приложение спрашивает их при каждом подключении.
- На сервере приложение выполняет только фиксированный набор команд (подкоманды `ostp manage`, обновление, перезапуск, перезагрузка, удаление, панель, сертификат, подписки); произвольную команду страница отправить не может.

## Системные интерфейсы
- **Системный прокси Windows** (`sysproxy.rs`): записывает и восстанавливает значения прокси WinINet; исключённые домены попадают в список обхода и в punycode, и в читаемом виде.
- **TUN-адаптеры** (`ostp-tun`): Wintun на Windows, нативные TUN-устройства на Linux/macOS; пользовательский стек `netstack-smoltcp` восстанавливает TCP/UDP-потоки из сырых IP-пакетов адаптера.
- **Исключения по процессу** (`process_lookup.rs`): находят программу за локальным сокетом через `GetExtendedTcpTable`/`GetExtendedUdpTable` на Windows и `/proc/net` на Linux, в режимах TUN и прокси, так что правила обхода по процессу (§[`client.md`](client.md)) работают без драйвера ядра.
