# Архитектура

OSTP (Ospab Stealth Transport Protocol) — зашифрованный туннель, написанный на Rust поверх Tokio. На этой странице показано, как крейты связаны между собой и как кадрируется пакет.

## Крейты

1. **ostp-core**: движок протокола. Содержит конечный автомат `ProtocolMachine`, драйвинг Noise-рукопожатия, AEAD-кадрирование, обфускацию заголовков, адаптивный паддинг, прикладной уровень мультиплексирования `RelayMessage` и контроллер перегрузки (медленный старт, затем CUBIC). Полностью `sans-io` — без собственной сетевой логики.
2. **ostp-client**: клиентский демон. Запускает двухрежимный SOCKS5/HTTP-прокси и/или виртуальный TUN-адаптер, управляет логикой NAT/исключений и поддерживает зашифрованную сессию до удалённого сервера, перенося её на новый сокет того же транспорта при смене сети (роуминг).
3. **ostp-server**: высоконагруженный диспетчер. Демультиплексирует входящие датаграммы по session ID, обслуживает сессии, обрабатывает IP-роуминг, проксирует расшифрованный трафик в открытый интернет и опционально размещает Management API, встроенный DNS-резолвер и TCP fallback-слушатель.
4. **ostp-tun**: платформенные привязки TUN-адаптера (Windows/Wintun, Linux, macOS), общие для клиента и вспомогательного процесса GUI.
5. **ostp-tun-helper**: небольшой отдельно-привилегированный процесс, который десктопный GUI запускает для создания/владения TUN-адаптером, чтобы самому GUI не требовались повышенные права.
6. **ostp-jni**: JNI-привязки для Android (нативные методы `OstpClientSdk`: старт/стоп клиента, метрики, логи, пробер, подписки, управление сервером), встраивающие клиентский движок в приложение Flutter/Android через изолированные среды выполнения Tokio.
7. **ostp-dns**: фильтрующий DNS-резолвер, который сервер держит для своих клиентов (списки блокировки, правила, подмены, кэш).
8. **ostp-ssh**: SSH-клиент, которым оба приложения ставят OSTP на сервер и управляют им: вход по паролю или ключу, запомненный ключ хоста, команды от root, локальный проброс порта к веб-панели и список сохранённых серверов с запечатанными секретами (см. [`integrations.md`](integrations.md)).
9. **ostp**: единый CLI-бинарник — запускает движок в режиме сервера, клиента или relay, а также хостит подкоманды `setup`/`init`/`gk`/`links`/`connect`/`migrate`/`update`/`cert`/`sub`/`panel`/`dns`/`manage`/`changelog` (см. [`client.md`](client.md) / [`server.md`](server.md)).

Ещё две прикладные оболочки используют эти крейты, но лежат вне Cargo-workspace: **ostp-gui** (десктоп-приложение на Tauri для Windows и Linux) и **ostp-flutter** (кроссплатформенное мобильное приложение, Android — через `ostp-jni`). См. [`integrations.md`](integrations.md).

## Внешний конверт vs. вложенный кадр

У OSTP два разных уровня кадрирования (полная раскладка байт — в [`specification.md`](specification.md)):

1. **Внешний конверт на проводе** — `[masked session_id : 4][masked nonce : 8][AEAD ciphertext+tag]` для датаграмм данных, либо `[masked session_id : 4][masked noise_len : 2][noise_payload][random padding]` во время рукопожатия. Именно это когда-либо касается сети; первые 12 (или 6) байт маскируются XOR'ом как единый блок маской HMAC-SHA256, выведенной из полезной нагрузки самого пакета.
2. **Вложенный `FrameHeader`** — открытый текст, восстановленный *после* расшифровки AEAD. Фиксированный размер 12 байт:

| Смещение (байт) | Тип данных | Имя поля | Описание |
| :--- | :--- | :--- | :--- |
| 0 | `u8` | `version` | Версия формата вложенного кадра (текущая: `1`) |
| 1 | `u8` | `kind` | Тип кадра (см. ниже) |
| 2–3 | 2×`u8` | *(случайные)* | Заполняются случайными байтами (не нулями), чтобы избежать известного открытого паттерна внутри зашифрованной области — поля `flags` не существует |
| 4-5 | `u16 BE` | `stream_id` | Зарезервировано под будущее покадровое мультиплексирование; `0` в управляющих кадрах |
| 6-9 | `u32 BE` | `payload_len` | Длина полезной нагрузки в байтах |
| 10-11 | `u16 BE` | `pad_len` | Длина добавленного случайного паддинга |

### Типы кадров (`FrameKind`)
- `1 - Handshake`: зарезервировано; сообщения рукопожатия на деле идут во внешнем конверте, а не как вложенный кадр.
- `2 - Data`: несёт `RelayMessage` (см. ниже).
- `3 - Close`: сигнализирует закрытие сессии.
- `4 - KeepAlive`: поддерживает NAT-привязки живыми.
- `5 - Nack`: явный отрицательный ACK, запрашивающий немедленную ретрансмиссию.
- `6 - Ack`: кумулятивное + выборочное подтверждение.

Полная вложенная запись (`FramedPacket`) — это `[12 байт FrameHeader] + [N байт Payload] + [M байт Padding]`, и именно эта запись целиком шифруется AEAD, порождая шифротекст внешнего конверта.

## Прикладное мультиплексирование (`RelayMessage`)

Полезная нагрузка кадра `Data` — это `RelayMessage`, закодированное по схеме tag-length-value: `Connect(addr)`, `Data(bytes)`, `Close`, `ConnectOk`, `Error(msg)`, `Ping`/`Pong(ts)`, `UdpAssociate`, `UdpData(addr, bytes)`, `KeepAlive`. Именно этот уровень реально мультиплексирует множество проксируемых TCP-соединений и UDP-потоков поверх одной зашифрованной сессии — поле `stream_id` во вложенном `FrameHeader` пока не используется для демультиплексирования; порядок конкретного проксируемого соединения задаётся неявно порядком его сообщений `Connect`/`Data`/`Close`.

## Механизм надёжной доставки (ARQ)

`ostp-core` реализует собственный Selective-Repeat ARQ поверх ненадёжного транспорта:

1. **Нумерация кадров**: каждому кадру данных присваивается строго возрастающий 64-битный `nonce`, который одновременно служит порядковым номером ARQ и AEAD-nonce.
2. **История отправки (`sent_history`)**: отправленные датаграммы кэшируются до подтверждения, максимум `max_sent_history` (по умолчанию на сервере/клиенте: 32 768) записей.
3. **Быстрый путь Nack**: при обнаружении пробела в последовательности приёмник немедленно шлёт ограниченный по частоте `Nack` (не чаще раза в `max(10мс, RTO/2)`) с именем самого младшего пропущенного nonce; отправитель находит его в `sent_history` и повторно отправляет немедленно, минуя цикл тайм-аутов.
4. **Повтор по тайм-ауту**: периодическое событие `OstpEvent::Tick` повторно отправляет любой кадр, просрочивший адаптивный RTO (RFC 6298, `[50мс, 16с]`), с экспоненциальным бэкоффом до 64×, бюджетом `max(2, cwnd_packets/4)` (не более 64) ретрансмиссий за тик.
5. **Доставка не по порядку (`reorder_buffer`)**: кадры, пришедшие раньше своей очереди, лежат в `BTreeMap` (максимум `max_reorder_buffer`, по умолчанию 8192) до закрытия пробела, затем доставляются по порядку.
6. **Вытеснение «зомби» и восстановление после провала**: кадр, повторённый больше `max_retries + 2` раз (по умолчанию `max_retries` = 8), удаляется из `sent_history` и больше никогда не будет ретранслирован. Если из-за этого курсор ожидаемого nonce у приёмника застревает без продвижения на `clamp(8×RTO, 2с, 10с)`, приёмник намеренно перескакивает невосстановимый nonce, доставляет всё уже буферизованное за ним и принудительно шлёт `Ack` — меняя один потерянный кусок на восстановление сессии, которая иначе замёрзла бы навсегда.

## Контроль перегрузки

`ostp-core::congestion` держит окно и оценку RTT для каждой сессии. Медленный старт начинается с 32 пакетов. Одна потеря в этой фазе даёт лёгкое сокращение окна, и медленный старт продолжается; 3 и более потерь за 500 мс или сглаженный RTT вдвое выше минимального его заканчивают. Дальше окно растёт по CUBIC (RFC 9438). Сглаженный RTT вчетверо выше минимального считается стоячей очередью, и окно уменьшают, чтобы её слить. Отправка идёт с темпом `cwnd / min_rtt`, окно не больше 8192 пакетов. RTO считается по RFC 6298 (SRTT/RTTVAR) с правилом Карна: ретранслированный кадр никогда не берётся как замер RTT.

## Динамический роуминг

Привязка сессии идёт по криптографическому `session_id`, а не по сетевому адресу. Когда клиент переключает сеть (например, LTE на Wi-Fi) или текущий путь перестаёт отвечать:
1. Клиент открывает новое соединение тем же транспортом и переносит на него ту же сессию, без нового рукопожатия.
2. Сервер принимает датаграмму с нового адреса, проверяет AEAD и переключает обратный адрес сессии, только если nonce пакета новее всех принятых. Повтор старого пакета адрес не меняет.
3. Проксируемые TCP/UDP-потоки клиента остаются живы; неподтверждённые данные переотправляются по новому пути.
4. Если сервер не ответил (сессия истекла или транспорт заблокирован), клиент сообщает об этом в логе и сам ничего больше не делает: транспорт выбирает пользователь.

Подробности — в [спецификации, §9.6](specification.md). Поиск сессии для незнакомого адреса ограничен token bucket (всплеск на 50 токенов, пополнение 50/с), чтобы флуд с подделкой источника не мог навязать неограниченную работу.

## Подсистемы на стороне сервера

Помимо ядра диспетчера/ARQ, `ostp-server` хостит несколько опциональных подсистем, каждая настраивается независимо — подробности в [`server.md`](server.md):

- **Management API** (`api.rs`): REST API для статистики, CRUD пользователей/ключей, лимитов трафика, аудит-лога и правил маршрутизации, с аутентификацией по Bearer-токену или логину на основе хэша пароля; без одного из них не запускается.
- **Файл статистики трафика**: трафик пользователей раз в 30 секунд пишется рядом с конфигом; его читает `ostp manage` (это приложения запускают по SSH).
- **DNS-резолвер** (`dns.rs`): фильтрация по AdBlock-спискам и форвардинг DNS-over-HTTPS для уже туннелированных клиентов, с ограниченным по частоте путём ответов.
- **Fallback-слушатель** (`fallback.rs`): прозрачно перенаправляет неаутентифицированные TCP-соединения (пробы DPI, сканеры) на реальный бэкенд (например, локальный nginx), так что активный проб видит обычный сайт вместо закрытого порта или аномального протокола.
- **Цепочка исходящего трафика** (`outbound.rs`): исходящий трафик через вышестоящий SOCKS5-прокси, с маршрутизацией по правилам (суффикс домена / CIDR / протокол) в proxy, direct или block.
- **Узел-ретранслятор** (`relay_node.rs`): режим `relay`. Пересылает UDP- и UoT-трафик клиентов на один заданный сервер и ничего не проверяет: сессии сквозным образом аутентифицирует целевой сервер.
- **Мост overnet**: необязательный. Направляет имена `.ov` на локальный шлюз overnet и может открыть выход для пользователей overnet (см. [`server.md`](server.md)).
