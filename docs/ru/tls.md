# Домены и TLS

OSTP можно привязать к доменному имени. Тогда к нему подключаются по настоящему HTTPS на порту 443, с сертификатом Let's Encrypt, который продлевается сам. Это необязательно: обычный UDP и UoT на собственном порту сервера (по умолчанию 50000) работают как раньше.

Это не мимикрия под протокол. У сервера настоящий сертификат на настоящий домен, и он сам завершает настоящий TLS. Со стороны это обычный HTTPS-сайт, а поток OSTP идёт внутри этого TLS без изменений. Для активного зонда, который не является клиентом, домен выглядит как веб-сервер, отвечающий 404 (или как ваш собственный сайт, если настроен fallback).

## Что идёт по проводу

**TLS завершает сам OSTP** (на машине нет веб-сервера, или клиент подключается прямо к порту OSTP):

```
TCP → TLS 1.3 (сертификат на vpn.example.com)
        └─ [u16 длина][датаграмма OSTP] [u16 длина][датаграмма OSTP] …
```

**Порт 443 держит веб-сервер (nginx / apache / caddy):**

```
клиент ──TLS──► nginx :443 ──TCP по loopback──► OSTP 127.0.0.1:50000

внутри TLS:
  GET /<секретный путь> HTTP/1.1       Upgrade: websocket, Connection: Upgrade
  ◄ HTTP/1.1 101 Switching Protocols   (отвечает OSTP, nginx пересылает)
  [u16 длина][датаграмма OSTP] …       те же кадры UoT, что и выше
```

Как WebSocket выглядит только рукопожатие: именно оно переключает веб-сервер в режим туннеля байтов. После `101` никакого WebSocket-кадрирования нет, идут только кадры UoT. Это работает через nginx, apache и caddy, которые после `101` пересылают байты вслепую. Через CDN, которые проверяют WebSocket-кадры, это **не** работает.

Что видит наблюдатель в обоих случаях: TLS-рукопожатие с `SNI=vpn.example.com` и `ALPN=http/1.1`, затем зашифрованные записи. TLS скрывает содержимое, но не скрывает размер и тайминги трафика.

## Как сервер различает соединения

Каждый TCP-слушатель OSTP смотрит на первый байт нового соединения:

| Первый байт | Что это | Обработка |
|---|---|---|
| `0x00`–`0x05` | UoT как есть (старший байт длины кадра ≤ 1535) | UoT, как раньше |
| `0x16` | TLS ClientHello | TLS с сертификатом сервера, затем классифицируется заново |
| `A`–`Z` | HTTP-запрос | `GET <ws_path>` с корректным upgrade → `101` и дальше UoT; остальное → заглушка |
| другой | что-то ещё | уходит в UoT, как и раньше |

Заглушка — это пустой `404`. Если включён `fallback.enabled`, соединение вместо этого прокидывается на `fallback.target`, то есть на настоящий сайт. На классификацию отводится 10 с, заголовки не больше 8 КиБ.

Секретный путь сравнивается за постоянное время. Запрос на правильный путь с неправильными заголовками получает ту же заглушку, что и любой другой.

Соединения с loopback считаются локальным веб-сервером. Для них лимит на клиента (10 новых соединений за 10 с) считается по `X-Real-IP` / `X-Forwarded-For`. От всех остальных эти заголовки игнорируются.

## Настройка

На сервере, от root:

```bash
ostp cert issue
```

Команда спросит:

1. **Домен.** Его A/AAAA-запись должна указывать на этот сервер. Команда это проверит и предупредит о расхождении.
2. **Кто обслуживает 443.** Команда ищет nginx, apache и caddy:
   - **Нашёлся:** после явного «да» в него добавляется сайт для домена.
     - **Что добавляется:** секретный путь переключается (upgrade) и проксируется в OSTP, `/<webpath>/` ведёт в панель (если она включена), а `/.well-known/acme-challenge/` уходит на ACME-ответчик OSTP по адресу `127.0.0.1:50080`. Всё остальное получает 404.
     - **Как применяется:** перед изменением делается бэкап, конфиг проверяется собственной проверкой веб-сервера (`nginx -t`, `apachectl configtest`, `caddy validate`), затем веб-сервер перезагружается. Если хоть что-то из этого не прошло, изменения откатываются, и веб-сервер остаётся как был.
   - **Не нашёлся:** OSTP сам слушает **443** (только TLS: OSTP, панель под `/<webpath>/`, иначе 404) и **80** (ACME-челленджи и редирект на https для всего остального).
3. **Сертификат:**
   - **caddy:** продолжает сам выпускать и продлевать свой сертификат, OSTP его не трогает.
   - **nginx, apache или собственный 443 OSTP:** Let's Encrypt через HTTP-01. Нужно указать email для связи (необязательно), принять Subscriber Agreement и при желании выбрать staging-CA для первой пробы. Чтобы использовать свой сертификат, передайте `--cert-path/--key-path`.

Затем команда выпускает сертификат, печатает ссылки и предлагает перезапустить сервис. Без вопросов:

```bash
ostp cert issue --domain vpn.example.com --email admin@example.com --agree-tos --frontend auto --yes
```

Мастер `ostp setup` в серверных режимах предлагает тот же шаг в конце.

| Команда | Что делает |
|---|---|
| `ostp cert status` | домен, фронтенд, издатель, срок, следующее продление |
| `ostp cert renew [--force]` | продлить сейчас |
| `ostp links` | для каждого ключа: TLS-ссылка на домен и UDP-ссылка |
| `ostp uninstall` | заодно убирает сайт, добавленный в nginx/apache/caddy |

Порты: откройте в фаерволе **443/tcp** (и **80/tcp** для Let's Encrypt). Сам `ostp` правила фаервола не меняет.

## Продление

Когда `tls.cert` равен `"acme"`, работающий сервис сам следит, чтобы сертификат был действителен.

Сертификат выпускается сразу, если:
- сертификата ещё нет или есть только самоподписанная заглушка;
- сертификат staging, а в конфиге указан боевой, или наоборот;
- в сертификате нет имени домена.

В остальных случаях продление идёт, когда остаётся треть срока (30 дней для 90-дневного сертификата), или за `renew_days_before` дней до истечения.

Новый сертификат подставляется без перезапуска. После этого выполняется `reload_command`, чтобы его подхватил веб-сервер.

Ошибки пишутся в лог, повтор через 1 ч, затем интервал удваивается до 24 ч. Прежде чем обращаться к Let's Encrypt, сервер запрашивает собственный URL челленджа. Поэтому ошибки DNS или фаервола вылезают сразу и не расходуют лимит неудачных проверок Let's Encrypt.

До первого выпуска отдаётся самоподписанная заглушка, так что TLS и проверка конфига веб-сервера работают с самого начала.

Файлы лежат рядом с конфигом:
- `certs/<домен>/{fullchain,privkey}.pem` — ключ с правами 0600;
- `acme/` — аккаунт, ожидающие челленджи и блокировка, общая с CLI.

## Конфигурация сервера

```jsonc
"domain": "vpn.example.com",   // идёт в ссылки, с TLS или без
"tls": {
  "enabled": true,
  "frontend": "builtin",        // builtin | nginx | apache | caddy
  "ws_path": "/Xk3pQ9aZr2…",     // секретный путь для upgrade (не меньше 8 символов после "/")
  "cert": "acme",               // acme | manual | none (caddy)
  "cert_path": "…", "key_path": "…",  // по умолчанию <папка конфига>/certs/<домен>/…
  "acme": {
    "email": "admin@example.com",
    "staging": false,
    "directory": null,          // другой ACME-CA
    "responder": "127.0.0.1:50080",
    "renew_days_before": null
  },
  "https_listen": ["0.0.0.0:443"],  // только для builtin
  "http_listen": ["0.0.0.0:80"],    // только для builtin
  "public_port": 443,               // порт, который попадает в ссылки
  "reload_command": "systemctl reload nginx || nginx -s reload"
}
```

Настройки TLS читаются при старте, поэтому после их изменения перезапустите сервис (`ostp cert issue` это предлагает). Файлы сертификата перечитываются сами.

## Клиенты

Опции транспорта (только для UoT):

| Поле | Значение |
|---|---|
| `tls` | завернуть UoT в TLS |
| `tls_sni` | имя сервера для TLS; по умолчанию хост из адреса сервера |
| `tls_insecure` | принимать любой сертификат. **Только для тестов**: кто угодно на пути сможет выдать себя за сервер |
| `ws_path` | путь для upgrade; обязателен, если перед OSTP стоит веб-сервер |

Сертификат проверяется по встроенному набору корневых сертификатов Mozilla. Это одинаково работает на Android, Windows и минимальном Linux.

SNI и `Host` всегда берутся из настроенного имени, а не из разрешённого адреса, в том числе при запасном пути через NAT64.

Внутри TLS junk-пакеты и фрагментация первого пакета отключаются: под шифрованием они ничего не скрывают.

Ссылки несут те же опции: `ostp://KEY@vpn.example.com:443?type=uot&tls=1&path=%2FXk3p…`. Все параметры описаны на странице Share Links. В Android-приложении и десктопном GUI те же переключатели есть в редакторе профиля; «не проверять сертификат» там помечен как небезопасный.

## Подписки

Когда настроены домен и TLS, сервер может выдавать каждому пользователю ссылку подписки `https://vpn.example.com/sub/<токен>`. По ней отдаются актуальные ссылки этого пользователя: сначала TLS, затем UDP. Приложения периодически перечитывают подписку, поэтому смена порта, пути или настроек сертификата на сервере доходит до клиентов без раздачи новых ссылок.

```jsonc
"subscription": {
  "enabled": true,
  "path": "/sub",                 // префикс URL
  "name": "Мой VPN",              // заголовок в приложениях; по умолчанию домен
  "update_interval_hours": 12,    // как часто приложения обновляют подписку
  "include": ["tls", "udp"]       // какие ссылки отдавать
}
```

Подписки ничто не включает само: ими управляет отдельная команда.

```
ostp sub status                       # включены ли, с какими настройками, чего не хватает
ostp sub enable [--path /sub] [--name "Мой VPN"] [--interval 12] [--include tls,udp]
ostp sub set --interval 6             # поменять настройки, не включая и не выключая
ostp sub disable
ostp sub urls [номер|имя|ключ]        # URL подписки пользователей
```

Каждая команда меняет ровно то, что названо, сохраняет копию конфига в `config.json.bak` и не перезапускает службу: изменения вступают в силу после `systemctl restart ostp`. Если 443 держит nginx, apache или caddy, путь подписки должен пробрасываться на OSTP. `ostp sub` сама веб-сервер не трогает: она печатает блок, который нужно добавить, а с флагом `--vhost` переписывает сайт, созданный OSTP (с проверкой конфига и откатом при ошибке).

URL для каждого ключа печатают также `ostp links` и `ostp links qr`, а в веб-панели он есть в окне «Поделиться».

- Токен — это хеш ключа доступа. Сам ключ в URL не попадает, поэтому его нет в журналах веб-сервера, но токен всё равно даёт доступ к ссылкам: передавайте URL подписки так же осторожно, как ключ.
- Подписка отдаётся только внутри TLS или локальному веб-серверу (nginx, apache, caddy), который сам завершил TLS. Открытым HTTP на порту OSTP она не отдаётся.
- На неизвестный токен сервер отвечает той же заглушкой, что и на любой другой путь.
- По умолчанию ответ — ссылки по одной в строке. С `Accept: application/json` или `?format=json` ответ — JSON с именем, интервалом обновления, ссылками и расходом трафика. Заголовки `Profile-Update-Interval`, `Profile-Title` и `Subscription-Userinfo` понимают и сторонние менеджеры подписок.

Клиенты: в Android-приложении и десктопном GUI импорт принимает и `https://`-ссылку подписки (вручную, из буфера или по QR). Для подписки появляется карточка с расходом и кнопкой обновления, а её профили переписываются при каждом обновлении. CLI: `ostp import https://…/sub/…`.
