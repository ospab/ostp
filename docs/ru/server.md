# Серверный демон OSTP

## Обзор
Сервер OSTP — это высокопроизводительный сетевой шлюз, рассчитанный на одновременное обслуживание тысяч анонимных обфусцированных туннелей. Он демультиплексирует входящие датаграммы, расшифровывает инкапсулированную нагрузку и проксирует трафик к целевым узлам в открытом интернете — опционально предоставляя рядом с самим туннелем management API, встроенный DNS-резолвер и decoy-слушатель (fallback).

---

## Архитектура диспетчера (Dispatcher Core)

Ядро сервера — централизованный модуль `Dispatcher`. В отличие от классических синхронных схем «поток на сокет», он строго разделяет сетевой ввод-вывод и состояние сессий:

1. **Асинхронный опрос сокета**: независимая асинхронная задача непрерывно читает датаграммы из слушающего(их) сокета(ов) — UDP и/или UoT/TCP — и передаёт их диспетчеру.
2. **Реестр криптосессий**: диспетчер поддерживает хэш-таблицу всех активных сессий, индексированную по `session_id`.
3. **Маршрутизация без копирования**: для каждой входящей полезной нагрузки диспетчер выполняет поиск `session_id` за `O(1)`. При совпадении шифротекст передаётся напрямую в `ProtocolMachine` этой сессии.
4. **Путь перебора рукопожатия**: датаграмма от нераспознанного источника не несёт открытого идентификатора ключа (так задумано — см. [`obfuscation.md`](obfuscation.md)), поэтому она пробно обрабатывается против кэшированных производных секретов каждого зарегистрированного ключа. Этот путь ограничен глобальным token bucket (по умолчанию 100 попыток/с) независимо от быстрого пути установленных сессий, что ограничивает затраты CPU на флуд с подделкой источника.

## Защита от атак и устойчивость к вторжениям

Поскольку публичные конечные точки постоянно подвергаются пробному трафику и попыткам DoS, сервер реализует несколько уровней защиты:

### 1. Изолированное отбрасывание пакетов
Любой повреждённый кадр, сбой AEAD-аутентификации или некорректный протокольный пакет мгновенно приводит к молчаливому отбрасыванию:
- Ошибки обработки локализуются сразу на этапе первичного извлечения.
- Существующие аутентифицированные сессии **никогда не завершаются и не сбрасываются** из-за невалидного пакета, пришедшего с совпадающим ID. Это блокирует атаки слепой подстановки пакетов (spoofing), нацеленные на разрыв чужих туннелей.

### 2. Защита от повторного воспроизведения (Replay)
Против злоумышленника, перехватывающего и позже повторно отправляющего валидные датаграммы рукопожатия:
- Клиентские рукопожатия несут в полезной нагрузке криптографическую временную метку.
- Сервер сверяет её с окном синхронизации ±300 секунд.
- Принятые рукопожатия записываются в ограниченный по размеру anti-replay кэш (по умолчанию 50 000 записей), чтобы категорически отбрасывать точные побайтные повторы.

### 3. Лимиты сессий и попыток
- Число одновременных сессий жёстко ограничено (по умолчанию 1024); рукопожатия сверх лимита молча отбрасываются вместо вытеснения существующей сессии.
- Сессии, простаивающие 600 секунд (10 минут — с запасом на типичные задержки перепривязки мобильного NAT), вытесняются диспетчером.

## Роуминг клиента без задержек

Сервер считает координаты IP:порт изменчивыми, отслеживая сессии по `session_id`:
- При получении **любого успешно расшифрованного и аутентифицированного** кадра данных диспетчер считывает его исходный IP и порт.
- Если этот адрес отличается от записанной для сессии координаты, сервер выполняет атомарное обновление на месте — без перезапуска рукопожатия.
- Последующие исходящие пакеты для клиента направляются на обновлённый адрес.
- Путь перепривязки ограничен собственным token bucket (всплеск на 50 токенов, пополнение 50/с), чтобы флуд с подделкой источника не мог навязать неограниченную работу по сканированию роуминга; на уже текущий, уже аутентифицированный трафик это ограничение не влияет.
- Это обеспечивает переключение между сотовыми вышками или сетями Wi-Fi за миллисекунды, полностью сохраняя вышестоящие TCP-сессии.

## Management API

Опциональный REST API (`api.rs`), включаемый блоком `api` в `config.json`, предоставляет статус сервера, статистику трафика по пользователям и управление ключами — для построения панелей/дашбордов (например, в стиле 3x-ui):

- **Аутентификация**: либо статический Bearer `token` (используется и для федерации relay-узлов, см. ниже), либо логин по паре логин/хэш пароля (`POST /login`), выдающий сессионный токен — сравнения выполняются за постоянное время во избежание timing-атак. Если не заданы ни токен, ни логин/хэш пароля, API открыт для любого, кто может достучаться до адреса привязки — привязывайте его к `127.0.0.1` и прикрывайте reverse-прокси для доступа извне.
- **Эндпоинты** (монтируются под настроенным `webpath`): `GET /server/status`, `GET`/`PUT /server/config`, `GET`/`POST /users`, `GET`/`PUT`/`DELETE /users/{key}`, `PUT /users/{key}/limit`, `POST /users/{key}/reset`, `POST /users/bulk`, `GET`/`POST`/`DELETE /audit`, `GET`/`PUT /router/rules`, а также `GET /subscribe/{key}` (без Bearer-токена — аутентифицирует запрос сам ключ доступа, возвращая готовую конфигурацию клиента или ссылку `ostp://`).
- Полный справочник запросов/ответов — на [странице Management API в вики](https://github.com/ospab/ostp/wiki/Management-API).

### Веб-панель: `ostp panel`

Панель встроена в бинарник и работает поверх того же API. Управление — отдельной командой:

```
ostp panel status                      # включена ли, адрес, путь, вход, как открыть
ostp panel enable [--bind 127.0.0.1:9090] [--webpath x7Kq2m] [--user admin]
ostp panel set --webpath x7Kq2m        # поменять настройки, не включая и не выключая
ostp panel passwd [--user NAME]        # пароль: запрашивается дважды без эха или читается из stdin
ostp panel token [--new | --clear]     # API-токен для скриптов
ostp panel disable
```

`enable` не включит панель без входа: если логин или пароль не заданы, команда их спросит. Пароль никогда не передаётся аргументом (он остался бы в истории shell) и должен быть не короче 8 символов. Каждая команда сохраняет копию конфига и перезапускает запущенную службу (`--no-restart`, чтобы не перезапускать).

Панель открывается на сервере по `http://127.0.0.1:9090/<webpath>/`, с другого компьютера — через SSH-туннель (`ssh -L 9090:127.0.0.1:9090 user@server`) или по HTTPS на домене, если 443 держит встроенный фронтенд либо веб-сервер пробрасывает путь панели (`ostp panel set --vhost`). `ostp panel status` показывает все доступные адреса.

## Встроенный DNS: `ostp dns`

Фильтрующий резолвер для клиентов, подключённых к серверу (крейт `ostp-dns`), — блокировка рекламы и трекеров по спискам, свои правила и имена, как в AdGuard Home. Это не DNS-туннель: трафик OSTP он не переносит.

**Снаружи он недоступен.** Отдельного порта нет: резолвер отвечает только на запросы, пришедшие через туннель. Когда фильтрация включена, через него проходит всё, что клиент резолвит:

| Как клиент ищет адрес | Что делает сервер |
|---|---|
| UDP на любой адрес `:53` (TUN-режим) | перехватывает и отвечает сам |
| TCP на любой адрес `:53` | перенаправляет на локальный DNS-over-TCP резолвера |
| DNS-over-TLS / DNS-over-QUIC (`:853`, TCP и UDP) | соединение отклоняется, приложение откатывается на обычный DNS (при `doh-bypass on`) |
| Шифрованный DNS по IP публичного резолвера (1.1.1.1, 8.8.8.8, Quad9, AdGuard, OpenDNS, Яндекс… на `:443`, TCP и QUIC) | отклоняется (при `doh-bypass on`). Так Android («Частный DNS: автоматически») и Chrome сами переходят на шифрованный DNS, когда системный DNS — 1.1.1.1 или 8.8.8.8, а мимо фильтра уходило бы почти всё |
| DoH браузера | канарейка `use-application-dns.net` → NXDOMAIN, известные DoH-хосты блокируются (при `doh-bypass on`) |
| SOCKS/прокси по имени (`CONNECT host:port`) | имя резолвится этим же резолвером: заблокированное — соединение отклоняется, переписанное — идёт на указанный адрес. С включённым outbound-прокси имя уходит в прокси как есть, но блокировка работает |

Конвейер обработки имени: свои имена (rewrites) → прочие `*.ostp` дают NXDOMAIN → безопасный поиск → блокировка обхода через DoH → блокировка сервисов → списки и свои правила → кэш → upstream → проверка CNAME (маскировка трекеров под свой домен ловится по цели CNAME).

```bash
ostp dns status                          # что включено, списки, число правил, upstream
ostp dns enable                          # включить (по умолчанию список AdGuard DNS filter)
ostp dns disable [--intercept-only]      # выключить; с --intercept-only DNS клиентов по-прежнему идёт через сервер, но без фильтрации
ostp dns update                          # скачать списки сейчас (иначе раз в 24 ч)
ostp dns test ads.example.com            # что будет с именем и каким правилом (офлайн, по скачанным спискам)

ostp dns list presets                    # встроенные списки: adguard, adaway, stevenblack, oisd-small, hagezi-light
ostp dns list add oisd-small             # по id или по URL; --allow — список исключений
ostp dns list show | remove | enable | disable
ostp dns block tracker.example.com       # ||tracker.example.com^
ostp dns allow cdn.example.com           # @@||cdn.example.com^
ostp dns rule add '||ads.*^$important'   # свои правила в синтаксисе adblock или hosts
ostp dns rewrite add panel.ostp 10.1.0.1 # свои имена; *.lan — для всех поддоменов
ostp dns service block tiktok            # целые сервисы; ostp dns service list — список
ostp dns safesearch on                   # Google, YouTube, Bing, DuckDuckGo, Яндекс
ostp dns doh-bypass on|off               # не давать браузерам обходить фильтр своим DoH/DoT
ostp dns mode nxdomain|null_ip|refused   # что получает заблокированное имя
ostp dns upstream add tls://dns.quad9.net   # https://…/dns-query, tls://, tcp://, udp:// или IP
ostp dns upstream mode fallback|parallel
```

Каждая команда проверяет настройки, делает `config.json.bak`, пишет секцию `"dns"` и перезапускает службу, если она запущена (`--no-restart` — не перезапускать). Скачанные списки хранятся в `<каталог конфига>/dns/lists/`, так что после перезапуска фильтрация работает сразу, даже без сети; неудачная загрузка оставляет прежнюю копию. Списки и upstream-запросы идут через outbound-прокси, если он включён.

**Своё имя для панели.** `10.1.0.1` — это сам сервер, каким его видят клиенты через туннель. После `ostp dns rewrite add panel.ostp 10.1.0.1` панель открывается у подключённого клиента по `http://panel.ostp:9090/<webpath>/` без SSH-туннеля (порт — из `ostp panel status`). Остальные имена в зоне `.ostp` получают NXDOMAIN и наружу не уходят.

**В панели** страница «DNS»: статистика (запросы, заблокировано, кэш, топ доменов и клиентов), журнал запросов с кнопками «Заблокировать»/«Разрешить», проверка имени, все настройки из списка выше. Сохранение применяется сразу, без перезапуска, и пишется в `config.json` с бэкапом.

Поддерживаемый синтаксис правил: `||домен^`, `@@||домен^`, `$important`, `*` в имени, строки `/etc/hosts` (`0.0.0.0 домен`, `127.0.0.1 домен`; любой другой адрес становится ответом). Правила-регулярки и правила с неизвестными модификаторами не применяются и считаются в `ostp dns status` как unsupported.

## Fallback (decoy) слушатель

Каждый TCP-слушатель OSTP смотрит на первый байт соединения: UoT обрабатывается как всегда, TLS завершается сертификатом сервера (если он настроен), а HTTP-запрос на секретный путь upgrade продолжается как UoT (так nginx/apache/caddy на 443 передают клиентов в OSTP). Всё остальное получает заглушку: голый 404 или — при `fallback.enabled` — прозрачную переброску на `fallback.target` (например, локальный nginx с обычным сайтом), так что активный зонд видит обычный сайт. `fallback.listen` добавляет ещё один такой слушатель. Домены, сертификаты и встроенный HTTPS-фронтенд описаны в [Домены и TLS](tls.md).

## Цепочка исходящего трафика (Outbound Chaining)

По умолчанию сервер проксирует расшифрованный клиентский трафик напрямую в интернет со своего адреса. `outbound.rs` опционально направляет часть или весь этот исходящий трафик через upstream SOCKS5/HTTP-прокси, с маршрутизацией по правилам (`domain_suffix`, `ip_cidr`, `protocol`), выбирающим `proxy`, `direct` или `block` — например, отправляя `.onion`-трафик в локальный Tor SOCKS-прокси, а всё остальное — напрямую.

## Федерация relay-узлов

`relay_node.rs` реализует облегчённый режим relay (`"mode": "relay"` в конфигурации) для построения цепочек: `Клиент → Relay₁ → Relay₂ → ... → Целевой сервер`. Relay-узел:

1. Принимает клиентские соединения по UDP и/или UoT, как обычный полноценный сервер.
2. Периодически синхронизирует текущий набор ключей доступа с Management API **целевого** сервера (`upstream_api_url` + `upstream_api_token`, интервал по умолчанию 30с), чтобы аутентифицировать клиентов без ручного зеркалирования ключей оператором.
3. Проверяет каждого клиента исключительно по HMAC/AEAD против синхронизированных ключей, затем пересылает авторизованный трафик дальше без изменений — relay-узел никогда не расшифровывает и не инспектирует туннелированную нагрузку, лишь убеждается, что клиент владеет валидным ключом, прежде чем ретранслировать его (по-прежнему сквозь-зашифрованные) байты дальше.

Это позволяет оператору прикрыть один целевой сервер расходуемыми relay-адресами, не доверяя самим relay-узлам содержимое трафика.
