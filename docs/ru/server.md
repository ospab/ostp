# Сервер

Сервер принимает сессии OSTP по UDP и UoT/TCP, расшифровывает их и пересылает трафик к адресатам. Рядом с туннелем он может держать management API с веб-панелью, фильтрующий DNS-резолвер и decoy-слушатель.

## Диспетчер

Все сокеты питают один `Dispatcher`, который разделяет сетевой ввод-вывод и состояние сессий:

1. Отдельная задача читает датаграммы из слушающих сокетов (UDP и/или UoT/TCP) и передаёт их диспетчеру.
2. Диспетчер держит хэш-таблицу активных сессий по `session_id`.
3. Датаграмма ищется по `session_id`; при совпадении шифротекст сразу идёт в `ProtocolMachine` этой сессии.
4. Датаграмма от неизвестного источника не несёт открытого идентификатора ключа (см. [obfuscation.md](obfuscation.md)), поэтому её пробуют расшифровать производными секретами каждого ключа доступа. У этого пути свой глобальный token bucket (по умолчанию 100 попыток в секунду), он ограничивает затраты CPU при флуде с подделанными адресами.

## Защита от атак

### 1. Плохие пакеты молча отбрасываются
Повреждённый кадр, неверный AEAD-тег или некорректный пакет отбрасываются без ответа. Установленная сессия не закрывается и не сбрасывается из-за невалидного пакета с её ID, так что поддельный пакет не может отключить пользователя.

### 2. Защита от повторов
Рукопожатие несёт временную метку Unix, которую сервер принимает в пределах ±300 секунд. Принятые рукопожатия попадают в ограниченный anti-replay кэш (50 000 записей), поэтому точная копия, повторённая в этом окне, отбрасывается.

### 3. Лимиты сессий и попыток
- Не больше 1024 сессий одновременно; рукопожатия сверх лимита отбрасываются, а не вытесняют существующую сессию. У одного ключа доступа не больше 32 сессий: новая вытесняет самую старую сессию этого ключа, так что один ключ не может занять все места.
- У одного ключа доступа одновременно не больше 4096 открытых соединений (TCP-потоков и UDP-ассоциаций); сверх этого клиент получает ошибку. Иначе один ключ мог бы исчерпать файловые дескрипторы процесса.
- Перебор ключей для неизвестной датаграммы (по операции X25519 на ключ) ограничен для каждого источника (адрес IPv4 или IPv6 /64: 5 в секунду, всплеск до 20) и для всего сервера (100 в секунду). Источники, прошедшие рукопожатие за последние 24 часа, общим лимитом не ограничиваются, поэтому флуд, поддельный или нет, не мешает вернуться уже подключавшимся; совсем новый клиент при флуде больше 100 датаграмм в секунду всё ещё может ждать.
- Сессия, простаивающая 600 секунд, удаляется (с запасом на перепривязку мобильного NAT).
- TCP- или TLS-соединение (UoT), по которому 5 минут не приходит ни одной целой датаграммы, закрывается. Клиенты шлют keepalive каждые несколько секунд, так что сюда попадают только мёртвые или брошенные соединения; сама сессия сохраняется и может продолжиться по новому соединению. За веб-сервером сайт, который пишет OSTP, закрывает соединение через те же 5 минут (`proxy_read_timeout 5m` в nginx, `timeout=300` в Apache).

### 4. Куда могут подключаться клиенты

Соединение клиента может идти в интернет. На самом сервере ему доступно только то, что предназначено клиентам: порт панели и DNS (порт 53). Частные сети (`10/8`, `172.16/12`, `192.168/16`, `100.64/10`, IPv6 `fc00::/7`) и остальной loopback сервера закрыты: там внутренняя сеть провайдера, базы данных и админки. Link-local и служебные диапазоны, включая сервис метаданных облака `169.254.169.254` с учётными данными инстанса, закрыты всегда. Проверяется адрес, к которому идёт соединение, после разрешения имени, для TCP и UDP.

Сервер на домашнем роутере, который должен пускать клиентов в свою локальную сеть или открывать через `10.1.0.1` другую локальную службу, включает это параметром `"local_access": true` на верхнем уровне конфига.

## Роуминг

Сессии отслеживаются по `session_id`, а не по адресу. Когда кадр, который расшифровывается и проходит проверку, приходит с другого IP или порта, сервер обновляет адрес сессии на месте, без нового рукопожатия, и отправляет ответы туда. Телефон, перешедший с Wi-Fi на сотовую сеть, сохраняет свои TCP-соединения. Путь перепривязки ограничен для каждого источника (20 в секунду, всплеск до 50) и для всего сервера (200 в секунду, кроме недавно аутентифицированных источников); трафик с текущего адреса это не затрагивает.

## Management API

Опциональный REST API (`api.rs`), включаемый блоком `api` в `config.json`, предоставляет статус сервера, статистику трафика по пользователям и управление ключами — для построения панелей/дашбордов (например, в стиле 3x-ui):

- **Аутентификация**: либо статический Bearer `token` (используется и для федерации relay-узлов, см. ниже), либо логин по паре логин/хэш пароля (`POST /login`), выдающий сессионный токен — сравнения выполняются за постоянное время во избежание timing-атак. Без входа (ни токена, ни логина с хэшем пароля) API не запускается вовсе, на каком бы адресе он ни слушал: `127.0.0.1` не защищает, потому что любой клиент попадает на loopback сервера через туннель как `10.1.0.1`. Пустой `"token": ""` считается отсутствием токена. Вход задаёт `ostp panel enable`.
- **Эндпоинты** (монтируются под настроенным `webpath`): `GET /server/status`, `GET`/`PUT /server/config`, `GET`/`POST /users`, `GET`/`PUT`/`DELETE /users/{key}`, `PUT /users/{key}/limit`, `POST /users/{key}/reset`, `POST /users/bulk`, `GET`/`POST`/`DELETE /audit`, `GET`/`PUT /router/rules`, а также `GET /subscribe/{key}` (без Bearer-токена — аутентифицирует запрос сам ключ доступа, возвращая готовую конфигурацию клиента или ссылку `ostp://`).
- Полный справочник запросов/ответов — на [странице Management API в вики](https://github.com/ospab/ostp/wiki/Management-API).

### Веб-панель: `ostp panel`

Панель встроена в бинарник и работает поверх того же API. Управление — отдельной командой:

```
ostp panel status                      # включена ли, адрес, путь, вход, как открыть
ostp panel enable [--bind 127.0.0.1:9090] [--webpath x7Kq2m] [--user admin]
ostp panel set --webpath x7Kq2m        # поменять настройки, не включая и не выключая
ostp panel passwd [--user NAME]        # пароль: запрашивается дважды без эха или читается из stdin
ostp panel token [--new | --clear]     # API-токен для скриптов
ostp panel disable
```

`enable` не включит панель без входа: если логин или пароль не заданы, команда их спросит. Пароль никогда не передаётся аргументом (он остался бы в истории shell) и должен быть не короче 8 символов. Хранится он с солью (PBKDF2-HMAC-SHA256, 300 000 раундов); голый SHA-256 из прошлых версий по-прежнему принимается, а `ostp panel status` просит задать пароль заново. Неудачные попытки входа ограничены на весь сервер: 10 в минуту; сверх этого какое-то время отклоняется любой вход, и с верным паролем тоже, а уже открытые сессии и CLI работают. Если `webpath` не задан, `enable` выбирает случайный. Каждая команда сохраняет копию конфига и перезапускает запущенную службу (`--no-restart`, чтобы не перезапускать).

Панель открывается на сервере по `http://127.0.0.1:9090/<webpath>/`, с другого компьютера — через SSH-туннель (`ssh -L 9090:127.0.0.1:9090 user@server`) или по HTTPS на домене, если 443 держит встроенный фронтенд либо веб-сервер пробрасывает путь панели (`ostp panel set --vhost`). На HTTPS-сайте панель отдаётся только по секретному `webpath`: по пути по умолчанию `/panel/` любой, кто зондирует сайт, увидел бы страницу входа OSTP. `ostp panel status` показывает все доступные адреса. Устройство, подключённое через этот сервер, открывает её по адресу `http://10.1.0.1:<порт>/<webpath>/`. Десктопное и Android-приложения открывают панель через своё SSH-соединение (*Server management → Management → Open the panel*), открытый порт не нужен. Вёрстка панели подстраивается под экран телефона.

## Статистика трафика и `ostp manage`

Раз в 30 секунд сервер пишет трафик пользователей в `.ostp_stats.json` рядом с конфигом (доступен только root; пишется во временный файл и переименовывается). Он же пишется при штатной остановке и читается при запуске, поэтому трафик и зависящие от него лимиты переживают перезапуск и обновление; пользователи, которых больше нет в конфиге, отбрасываются. Счётчики DNS и журнал запросов хранятся так же, в `.ostp_dns_activity.json` (только root, пишется раз в минуту и при остановке; «Очистить» в панели очищает и его).

`ostp manage` (скрыт из `--help`) выводит состояние сервера и применяет повседневные изменения одним JSON-объектом; при ошибке — `{"error": ...}` и код выхода 1. Вопросов он не задаёт и работает без терминала: именно это десктопное и Android-приложения запускают по SSH.

| Команда | Что делает |
|---|---|
| `ostp manage install [--port N] [--host H] [--user NAME]` | Первая установка: пишет конфиг сервера с одним пользователем, открывает порт в ufw или firewalld, если они включены, регистрирует и запускает службу. На настроенном сервере только проверяет, что служба запущена |
| `ostp manage status` | Версия, состояние службы, сеансы, пользователи, адрес, TLS-домен и сертификат, подписки, панель и система: ОС, нагрузка, память, диск |
| `ostp manage users` | Все пользователи со ссылками, URL подписки и трафиком |
| `ostp manage user-add NAME`, `user-remove WHO`, `user-rename WHO NAME` | WHO — номер (как в `ostp links`), имя или ключ. Работающий сервер подхватывает изменение из файла; последнего пользователя удалить нельзя |
| `ostp manage logs [-n N]` | Последние строки лога службы |
| `ostp manage restart` | Перезапускает службу и сообщает, поднялась ли она |

`install.sh -y [-b beta] [--port N] [--host H] [--user NAME]` ставит без мастера настройки и при первой установке запускает `ostp manage install`.

## Встроенный DNS: `ostp dns`

Фильтрующий резолвер для клиентов, подключённых к серверу (крейт `ostp-dns`), — блокировка рекламы и трекеров по спискам, свои правила и имена, как в AdGuard Home. Это не DNS-туннель: трафик OSTP он не переносит.

**Снаружи он недоступен.** Отдельного порта нет: резолвер отвечает только на запросы, пришедшие через туннель. Когда фильтрация включена, через него проходит всё, что клиент резолвит:

| Как клиент ищет адрес | Что делает сервер |
|---|---|
| UDP на любой адрес `:53` (TUN-режим) | перехватывает и отвечает сам |
| TCP на любой адрес `:53` | перенаправляет на локальный DNS-over-TCP резолвера |
| DNS-over-TLS / DNS-over-QUIC (`:853`, TCP и UDP) | соединение отклоняется, приложение откатывается на обычный DNS (при `doh-bypass on`) |
| Шифрованный DNS по IP публичного резолвера (1.1.1.1, 8.8.8.8, Quad9, AdGuard, OpenDNS, Яндекс… на `:443`, TCP и QUIC) | отклоняется (при `doh-bypass on`). Так Android («Частный DNS: автоматически») и Chrome сами переходят на шифрованный DNS, когда системный DNS — 1.1.1.1 или 8.8.8.8, а мимо фильтра уходило бы почти всё |
| DoH браузера | канарейка `use-application-dns.net` → NXDOMAIN, известные DoH-хосты блокируются (при `doh-bypass on`) |
| SOCKS/прокси по имени (`CONNECT host:port`) | имя резолвится этим же резолвером: заблокированное — соединение отклоняется, переписанное — идёт на указанный адрес. С включённым outbound-прокси имя уходит в прокси как есть, но блокировка работает |

Конвейер обработки имени: свои имена (rewrites) → прочие `*.ostp` дают NXDOMAIN → безопасный поиск → блокировка обхода через DoH → блокировка сервисов → списки и свои правила → кэш → upstream → проверка CNAME (маскировка трекеров под свой домен ловится по цели CNAME).

```bash
ostp dns status                          # что включено, списки, число правил, upstream
ostp dns enable                          # включить (по умолчанию список AdGuard DNS filter)
ostp dns disable [--intercept-only]      # выключить; с --intercept-only DNS клиентов по-прежнему идёт через сервер, но без фильтрации
ostp dns update                          # скачать списки сейчас (иначе раз в 24 ч)
ostp dns test ads.example.com            # что будет с именем и каким правилом (офлайн, по скачанным спискам)

ostp dns list presets                    # встроенные списки: adguard, adaway, stevenblack, oisd-small, hagezi-light
ostp dns list add oisd-small             # по id или по URL; --allow — список исключений
ostp dns list show | remove | enable | disable
ostp dns block tracker.example.com       # ||tracker.example.com^
ostp dns allow cdn.example.com           # @@||cdn.example.com^
ostp dns rule add '||ads.*^$important'   # свои правила в синтаксисе adblock или hosts
ostp dns rewrite add panel.ostp 10.1.0.1 # свои имена; *.lan — для всех поддоменов
ostp dns service block tiktok            # целые сервисы; ostp dns service list — список
ostp dns safesearch on                   # Google, YouTube, Bing, DuckDuckGo, Яндекс
ostp dns doh-bypass on|off               # не давать браузерам обходить фильтр своим DoH/DoT
ostp dns mode nxdomain|null_ip|refused   # что получает заблокированное имя
ostp dns upstream add tls://dns.quad9.net   # https://…/dns-query, tls://, tcp://, udp:// или IP
ostp dns upstream mode fallback|parallel
```

Каждая команда проверяет настройки, делает `config.json.bak`, пишет секцию `"dns"` и перезапускает службу, если она запущена (`--no-restart` — не перезапускать). Скачанные списки хранятся в `<каталог конфига>/dns/lists/`, так что после перезапуска фильтрация работает сразу, даже без сети; неудачная загрузка оставляет прежнюю копию. Списки и upstream-запросы идут через outbound-прокси, если он включён.

**Своё имя для панели.** `10.1.0.1` — это сам сервер, каким его видят клиенты через туннель. После `ostp dns rewrite add panel.ostp 10.1.0.1` панель открывается у подключённого клиента по `http://panel.ostp:9090/<webpath>/` без SSH-туннеля (порт — из `ostp panel status`). Остальные имена в зоне `.ostp` получают NXDOMAIN и наружу не уходят.

**В панели** страница «DNS»: статистика (запросы, заблокировано, кэш, топ доменов и клиентов), журнал запросов с кнопками «Заблокировать»/«Разрешить», проверка имени, все настройки из списка выше. Сохранение применяется сразу, без перезапуска, и пишется в `config.json` с бэкапом.

Поддерживаемый синтаксис правил: `||домен^`, `@@||домен^`, `$important`, `*` в имени, строки `/etc/hosts` (`0.0.0.0 домен`, `127.0.0.1 домен`; любой другой адрес становится ответом). Правила-регулярки и правила с неизвестными модификаторами не применяются и считаются в `ostp dns status` как unsupported.

## Fallback-слушатель

Каждый TCP-слушатель OSTP смотрит на первый байт соединения: UoT обрабатывается как всегда, TLS завершается сертификатом сервера (если он настроен), а HTTP-запрос на секретный путь upgrade продолжается как UoT (так nginx/apache/caddy на 443 передают клиентов в OSTP). Всё остальное получает заглушку: голый 404 или — при `fallback.enabled` — прозрачную переброску на `fallback.target` (например, локальный nginx с обычным сайтом), так что активный зонд видит обычный сайт. `fallback.listen` добавляет ещё один такой слушатель. Домены, сертификаты и встроенный HTTPS-фронтенд описаны в [Домены и TLS](tls.md).

## Исходящий прокси

По умолчанию клиентский трафик выходит с собственного адреса сервера. Секция `outbound` направляет часть или весь трафик через вышестоящий SOCKS5-прокси. Правила сопоставляют `domain_suffix`, `ip_cidr` и `protocol` и выбирают `proxy`, `direct` или `block` (остальное покрывает `default_action`), например `.onion` в локальный Tor, а всё прочее напрямую. В правиле можно задать `send_from` — локальный адрес источника; по умолчанию используется общий `bind_ip`.

## overnet: `.ov` для клиентов и выход

[overnet](https://github.com/ospab/overnet) — onion-сеть со своей зоной имён `.ov`. Она работает отдельным процессом рядом с сервером; сервер общается с ней только через локальные SOCKS5-порты. Протокол OSTP не меняется, поэтому это работает с любым клиентом 0.4.x.

```jsonc
"overnet": {
  "enabled": true,
  "entry": true,                    // клиенты открывают сайты .ov через этот сервер
  "gateway": "127.0.0.1:9150",      // SOCKS5-порт локального шлюза overnet
  "exit": false,                    // выпускать пользователей overnet в интернет через этот сервер
  "exit_listen": "127.0.0.1:9151"   // где слушает выход; только loopback
}
```

- **Вход.** Соединение к `name.ov` уходит в шлюз, в режиме прокси — по имени. В режиме TUN DNS сервера отвечает на `name.ov` фиктивным адресом из `198.18.0.0/15`, а соединения на этот адрес уходят в шлюз как `name.ov`. На `.ov` сервер отвечает сам, независимо от настроек `dns`. `.ov` никогда не попадает к DNS-апстримам и в интернет: при выключенном `entry` такие имена получают NXDOMAIN, а соединения отклоняются. Только TCP; UDP к `.ov` отбрасывается.
- **Выход.** По умолчанию выключен: всё, что выходит через exit, приписывается его адресу. SOCKS5-слушатель без аутентификации, поэтому привязывается только к loopback; локальный узел overnet отправляет туда соединения своих пользователей в обычный интернет. Они идут тем же путём, что и трафик клиентов (правила outbound, upstream-прокси, `bind_ip`, блок-листы DNS). Отклоняются: `.ov`, сам сервер, его туннельная сеть и частные, link-local и служебные диапазоны. Имена резолвятся и проверяются до соединения, если их не резолвит outbound-прокси.

Раздел **по умолчанию выключен**: ничего из overnet не работает, и установщик OSTP его не ставит. Владелец сервера включает раздел и ставит шлюз overnet сам (`scripts/install.sh --role gateway` из репозитория overnet). При включённом входе сервер раз в 5 секунд проверяет, принимает ли шлюз соединения; пока нет, `.ov` получает NXDOMAIN, а соединения отклоняются, как при выключенном входе, и это пишется в лог. Поэтому фиктивный ответ из 198.18.0.0/15 всегда означает, что шлюз на месте, — на это опирается `overnet browser`.

### Как включить

```bash
sudo ostp overnet install    # установщик overnet с ролью шлюза (systemd-служба overnet-gateway)
sudo ostp overnet enable     # раздавать .ov клиентам; перезапускает ostp (--no-restart, чтобы нет)
ostp overnet status          # секция, программа, отвечает ли шлюз, выход
sudo ostp overnet exit on    # по желанию: выход, затем `overnet relay --exit socks5://127.0.0.1:9151`
sudo ostp overnet disable    # выключить .ov (у выхода свой переключатель: exit off)
```

Те же переключатели есть на странице **overnet** веб-панели (применяются сразу, без перезапуска) и в десктопном и мобильном приложениях на вкладке управления сервером. `ostp check` показывает состояние секции. `ostp migrate` дописывает секцию в старый конфиг сервера, выключенной.

Клиентам ничего нового не нужно: в режиме TUN и через системный прокси `http://search.ov/` открывается в любом браузере. Пока `.ov` раздаётся, шифрованный DNS к публичным резолверам (DoT/DoQ на 853, DoH на адрес резолвера по 443) отклоняется, как при `dns.block_doh_bypass`: Chrome и Edge сами переходят на DoH, если системный DNS — 1.1.1.1 или 8.8.8.8, Android — при «Частный DNS: автоматически», а такой резолвер отвечает на `.ov` NXDOMAIN. После отказа устройство спрашивает обычный порт 53, а на нём отвечает сервер. Браузер, в котором DoH вручную закреплён за конкретным провайдером (Firefox «Максимальная защита», Chrome со своим провайдером), на `.ov` так и будет ошибаться: для этого подключения его нужно выключить.

## Узел-ретранслятор

`"mode": "relay"` запускает узел, который пересылает всё на один фиксированный сервер OSTP (`upstream_tcp` для UoT/TCP, `upstream_udp` для UDP): `Клиент -> Relay -> Сервер`. У ретранслятора нет ключей, и он ничего не решает: каждую сессию сквозным образом проверяет целевой сервер и отбрасывает неподходящие. Так перед одним сервером можно держать сменные адреса ретрансляторов, не доверяя им трафик. Ретранслятор держит не больше 4096 UDP-сессий и сбрасывает простаивающие. Настройка: `ostp init relay` или `ostp setup` (Linux, пункт 4). Параметры `upstream_api_url`, `upstream_api_token` и `sync_interval_secs` из старых конфигов игнорируются; `ostp migrate` их убирает.
