# Cloudflare WARP как выход сервера: проект

Статус: реализовано (крейт `ostp-warp`, команда `ostp warp`, пользовательская документация в [server.md](server.md#cloudflare-warp-как-выход-ostp-warp)); то, что требует настоящего устройства Cloudflare, вживую пока не проверено, см. «Как проверяется». Решения от 2026-11-12 отмечены. Где код расходится с планом, сказано в разделе «Отличия от плана».

## Зачем

Оператор не хочет, чтобы сайт видел адрес сервера. С WARP сайт видит адрес Cloudflare; Cloudflare видит адрес сервера и то, куда он подключается. Доверие переходит от хостинга к Cloudflare, а анонимности перед Cloudflare это не даёт. Адреса WARP общие и известны, поэтому на части сайтов будут капчи или отказ.

Официальный `warp-cli` в режиме прокси для этого не подошёл: в тесте оператора пропадал весь UDP, и пока он пропадал, адрес сервера мог утекать. Именно это проект должен исключить: UDP обязан работать, а у трафика, который должен идти через WARP, не должно быть способа выйти напрямую.

## Решения (2026-11-12)

1. **Клиент WireGuard внутри сервера `ostp` и локальный SOCKS5.** Туннель работает в пользовательском пространстве (без root, без модуля ядра, без изменения маршрутов хоста), а сервер SOCKS5 с TCP `CONNECT` и UDP `ASSOCIATE` слушает `127.0.0.1:40000` (настраивается). На него указывает существующий outbound-прокси сервера (`outbound`, который уже умеет SOCKS5 вместе с UDP).
2. **Два режима, выбираются командой.** `ostp warp enable --all` пускает через WARP всё, что сервер открывает наружу. `ostp warp enable --rules` пускает через WARP только то, что называют правила `outbound` (суффиксы доменов, подсети, протокол); остальное выходит напрямую, как написал оператор.
3. **Явная регистрация и необязательный ключ WARP+.** `ostp warp register --accept-terms` создаёт бесплатное устройство и сохраняет его ключи; `ostp warp license <ключ>` привязывает ключ WARP+. Сама ничего не регистрируется.

## Поведение

- **Без прямого отката.** В режиме `--all` при упавшем туннеле соединение не создаётся, а не уходит напрямую. TCP- и UDP-пути `outbound` уже отказываются отправлять напрямую, когда правило требует прокси; собственные запросы резолвера к вышестоящим серверам и загрузка списков получают то же правило.
- **DNS.** Имена разрешаются внутри туннеля (SOCKS5 с доменом, как `socks5h`), а не резолвером самого сервера. Списки DNS-фильтра и DoH-серверы сервера пользуются тем же прокси; сейчас это не работает с ошибкой `unsupported scheme socks5h`, потому что `ostp-dns` собран без функции `socks` у reqwest. Это исправляется первым.
- **IPv6.** WARP выдаёт устройству и адрес IPv6; назначения только с IPv6 идут через него. При упавшем туннеле они не проходят так же, как IPv4.
- **MTU.** 1280 внутри туннеля; TCP-сегменты режет под него пользовательский стек.
- **Keepalive.** 25 с, а рукопожатие повторяется, когда последнее старше предела WireGuard. Мёртвый туннель показывается в `ostp warp status` и в панели, а не скрывается повторами.

## Команды

```
ostp warp register --accept-terms   # создать устройство, ключи в warp.json (0600)
ostp warp license <ключ>            # привязать ключ WARP+
ostp warp enable --all | --rules    # записать конфигурацию, перезапустить службу, как другие команды
ostp warp disable
ostp warp status                    # зарегистрирован ли, режим, туннель, последнее рукопожатие, адрес снаружи
ostp warp test                      # TCP-запрос и UDP-запрос DNS через туннель; громко падает
ostp warp reset                     # забыть устройство (сначала спросит)
```

«Адрес снаружи» берётся из `https://www.cloudflare.com/cdn-cgi/trace`, запрошенного через туннель (`warp=on`).

## Конфигурация и файлы

- В `config.json` появляется раздел `warp` (`enabled`, `mode`, `listen`, `endpoint`), а схема версии 6 добавляет его выключенным, как было с `overnet`. Ключи лежат только в `warp.json` рядом с конфигурацией (0600), но не в `config.json`, резервной копии или журнале.
- Включение для `--all` записывает раздел `outbound` (SOCKS5 на `warp.listen`), а для `--rules` оставляет правила оператора на месте; выключение возвращает то, что было до этого (хранится в `warp.json`).
- В веб-панели появляется страница WARP: состояние, режим, адрес снаружи, регистрация и лицензия.

## Реализация

Новый крейт `ostp-warp`:

| Часть | Как |
|---|---|
| Регистрация | HTTPS к клиентскому API Cloudflare, как делает `wgcf`; хранит открытый ключ пира, точку входа, адреса устройства и его идентификатор клиента (проверить). |
| WireGuard | `boringtun` (реализация WireGuard на Rust от Cloudflare). Три «reserved» байта, которых WARP ждёт в заголовке пакета, выставляются из идентификатора клиента перед отправкой (проверить). |
| Стек | `smoltcp` поверх IP-пакетов туннеля, как в режиме TUN клиента; даёт сокеты TCP и UDP. |
| SOCKS5 | TCP `CONNECT` и UDP `ASSOCIATE`, только loopback. |

Работает задачей внутри процесса сервера, так что служба одна и команда одна — `ostp warp`. Сборки для MIPS остаются без него (см. «Отличия от плана»).

### Как выглядит сторона Cloudflare (как реализовано)

Взято из исходников других открытых реализаций; реализация ничего из этого вживую не вызывала (первый живой вызов делает оператор командой `ostp warp register`).

- База `https://api.cloudflareclient.com`, путь версии `v0a5641`, `User-Agent: 1.1.1.1/6.38.9-5641 (Android 16.0.0)`, `CF-Client-Version: a-6.38.9-5641`: `ViRb3/wgcf`, `cloudflare/api.go`.
- `POST /{v}/reg` с полями `fcm_token`, `install_id`, `key` (открытый ключ в base64), `locale`, `model`, `tos` (временная метка), `serial_number`, `os_version`, `key_type: curve25519`, `tunnel_type: wireguard`: тот же файл. `GET /{v}/reg/{id}` и `PUT /{v}/reg/{id}/account` (`{"license": ...}`), ответы с `id`, `token`, `account.account_type`, `config.client_id`, `config.interface.addresses.v4/v6`, `config.peers[].public_key`, `config.peers[].endpoint.host/v4/v6/ports`: `openapi-spec.yml` из `wgcf`. Спецификация даёт порты точки входа `[2408, 500, 1701, 4500]` по умолчанию; запись хоста `engage.cloudflareclient.com:2408`.
- Байты «reserved»: первые три байта декодированного из base64 `client_id` ставятся в байты 1–3 каждого сообщения WireGuard, отправляемого пиру, после того как сообщение (и его MAC) построено; во входящих эти байты обнуляются. Источники: Xray-core `proxy/wireguard/bind.go` (выставляются при отправке, обнуляются при приёме), крейт `warp-wireguard-gen` (`parse_client_id`) и `xdqi/warp-ebpf`.
- Не подтверждено: точный формат временной метки `tos` (код шлёт RFC 3339 UTC с миллисекундами и `Z`, как `warp-wireguard-gen`), принимает ли Cloudflare до сих пор эти версии клиента, и адрес условий (`ostp warp register` печатает `https://www.cloudflare.com/application/terms/`, взято по памяти).

## Риски

- Интерфейс регистрации Cloudflare — тот, которым пользуются её собственные приложения, а не документированный для сторонних; он может измениться, получить ограничения или отказать для адресов серверов. Действуют условия WARP, а `--accept-terms` — принятие их оператором, а не нами.
- Скорость ограничена одним ядром пользовательского WireGuard; замеряется в wirelab с локальным пиром WireGuard вместо Cloudflare, до любых обещаний.
- Точки входа WARP (UDP 2408 и другие) могут быть закрыты у некоторых хостингов.

## Как проверяется

Сделано, в `cargo test`:

- Модульные тесты `ostp-warp`: кадры SOCKS5 (с доменными именами и IPv6), reserved-байты, JSON регистрации по образцу в форме спецификации `wgcf`, `warp.json` (круг записи и чтения, атомарная замена, права 0600 в Unix, неизвестная версия отклоняется), секция конфигурации и что делает включение с `outbound`, DNS-запросы внутри туннеля, разбор trace.
- `ostp-server` (`warp::tests`): собственные `connect_target` и `connect_udp_target` сервера (код, который обслуживает клиентов) против настоящего SOCKS5-прокси и настоящего туннеля, где пир WireGuard — локальная замена Cloudflare (`ostp_warp::testpeer`: два туннеля `boringtun` по loopback и стек `smoltcp`, принимающий любой адрес). Покрыто: TCP по имени (разрешает резолвер пира), по адресу IPv4 и IPv6, UDP по адресу и по имени, reserved-байты на проводе, режим `rules` (подходящее правилу соединение идёт в туннель, прочее выходит напрямую), остановленный пир (TCP и UDP не работают при том, что цель доступна напрямую, и она насчитывает ноль принятых соединений), туннель, который так и не поднялся (все соединения отклоняются).
- `ostp` (`warp_cmd`): register, license (принята и отклонена), reset, enable, disable против локального поддельного сервиса регистрации (`ostp_warp::testapi`); без `--accept-terms` ничего не регистрируется; ключей нет в `config.json`; прежний `outbound` возвращается.
- `ostp-dns`: клиент прокси (имена SOCKS5 идут как имена, мёртвый прокси это ошибка).

Не покрыто и почему: настоящее устройство Cloudflare (правило было не обращаться к Cloudflare из тестов; первая живая проверка за оператором); пропускная способность (не измерялась); UDP-датаграмма больше MTU туннеля на настоящем пути; смена ключей после 2 минут длинной сессии; DoH фильтра DNS через прокси сквозным образом.

Запланировано для wirelab (не написано): один контейнер — замена WARP с обычным WireGuard (`wg-quick`, включены форвардинг и NAT), один с `ostp` и `warp.enabled`, пара ключей регистрации, записанная в `warp.json` вручную с открытым ключом и точкой входа замены, и контейнер-цель. Проверки: TCP, UDP (обмен QUIC и DNS) и IPv6 доходят до цели через пир, цель видит адрес пира, а не сервера, а при остановленном пире до цели не доходит ничего. Обычный пир `wg-quick` не понимает значения reserved-байтов, если его так не собрать; замене нужны три байта, обнулённые до расшифровки, как у Cloudflare.

## Отличия от плана

- Стек TCP/UDP туннеля — `smoltcp`, которым управляет одна задача-драйвер, а не код TUN клиента: тот привязан к устройству TUN и к обработке потоков клиента. `netstack-smoltcp` (его использует режим TUN клиента) применяется только на другом конце, в тестовом пире.
- MIPS: матрица релиза собирает `mipsel`; новые зависимости для него не проверены, а роутер плохо подходит для этого, поэтому `ostp-warp` там исключён через `cfg`, и `ostp warp` говорит об этом. На остальных целях он собирается (что проверено, см. журнал изменений и отчёт о работе).
- Фильтру DNS понадобилось больше, чем функция `socks`: при включённом прокси его обычные UDP-, TCP- и DoT-апстримы тоже выходили напрямую. Теперь они идут через прокси как DNS поверх TCP, а неприменимый прокси даёт отказ запросов и загрузки списков вместо отката.
- `ostp warp status` ещё читает `warp.status.json`, который работающий сервер пишет раз в 5 с, потому что туннель живёт в другом процессе; `test` и «адрес снаружи» идут через прокси как клиент, то есть проходят тем же путём, что и сервер, без второй сессии WireGuard на тех же ключах.
- Базовый адрес регистрации можно заменить переменной окружения `OSTP_WARP_API_BASE`; она нужна для тестов с локальным поддельным сервисом и как настройка не документируется.

## Открытые вопросы

1. Какие порты и адреса пробовать, когда `engage.cloudflareclient.com:2408` закрыт. Регистрация перечисляет порты 2408, 500, 1701 и 4500; сейчас используется только порт хоста (или `warp.endpoint`), другой оператор выбирает через `warp.endpoint`. Автоматический перебор остальных не сделан.
2. `--rules` берёт только правила, уже стоящие в `outbound`; список правил в командной строке не реализован.
3. Отклонённый ключ WARP+: `ostp warp license` завершается ошибкой с ответом сервиса и ничего не сохраняет, так что `status` отклонённого ключа не показывает. Как сервис ведёт себя, когда ключ позже истёк, неизвестно.
4. Сохранит ли Cloudflare WireGuard на этом интерфейсе регистрации (по сообщениям, WARP переводят на MASQUE).
