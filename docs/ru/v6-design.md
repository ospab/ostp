# Протокол v6: проект для 0.5.0

Статус: черновик, ничего из описанного здесь не реализовано. Действующий формат на проводе — версия 5 ([specification.md](specification.md)); 0.4.x остаётся на ней. Эта страница фиксирует, что меняется в 0.5.0 и зачем, чтобы код писался по плану.

## Принятые решения (2026-11-12)

1. **Клиент проверяет сервер.** Рукопожатие становится `Noise_NKpsk0_25519_ChaChaPoly_BLAKE2s`: клиент знает статический открытый ключ сервера, и первое сообщение шифруется на него. В v5 (`NNpsk0`) любой, у кого есть ключ доступа, может выдать себя за сервер.
2. **Переходный режим.** Сервер 0.5.0 принимает v6 и, за переключателем в конфигурации, v5; в 0.6 переключатель исчезает. Клиенты сами не откатываются: какую версию говорит клиент, входит в его профиль и выбирается пользователем, как и транспорт.
3. **Сначала план.** Эта страница и страница про потоки идут раньше кода. Старая ветка `claude/protocol-v6` (от beta.8) не перебазируется; v6 начинается от текущей alpha и забирает только уже проверенное там: HKDF с публичными метками (RFC 5869), защиту заголовка (RFC 9001 §5.4.4, вектор A.5), пролог Noise `ostp v6`, кодек RFC 6455.

## 1. Рукопожатие

### 1.1 Ключ сервера
- У сервера одна статическая пара X25519, создаётся при установке и хранится в его конфигурации рядом с ключами доступа.
- Открытый ключ едет вместе с профилем: новое поле в ссылках `ostp://` и в подписках. Профиль без него — профиль v5.
- Клиент, получивший не тот ключ сервера, что записан в профиле, останавливается и сообщает об этом; он не подключается и не спрашивает, доверять ли новому ключу. Замена ключа — явное действие на сервере (команда `ostp`) и новые ссылки.

### 1.2 Шаблон
```
<- s                         (известен заранее: открытый ключ сервера)
...
-> psk, e, es                (первое сообщение, уже зашифрованное на сервер)
<- e, ee
```
PSK по-прежнему выводится из ключа доступа (§6.1 спецификации): ключ доступа авторизует клиента, статический ключ удостоверяет сервер. Статического ключа у клиента нет; так сохраняется свойство, что клиент не оставляет ничего, что идентифицирует устройство. Статический ключ на устройство (`IKpsk2`) рассматривался ради лимита устройств и пока отклонён: он усложняет выдачу ключей и стоит анонимности; лимит можно построить на сессиях.

### 1.3 Рукопожатие должно выглядеть случайным
Сейчас эфемерный ключ X25519 лежит открыто со смещения 6, и его старший бит всегда равен нулю. Вместе с проверкой «точка на кривой» это отпечаток. В v6 всё сообщение Noise перед отправкой в сеть складывается по XOR с потоком ChaCha20; ключ потока берётся из PSK и случайного 12-байтового nonce, который идёт впереди. Elligator не нужен, потому что ключ нигде не виден без маски. Диапазон набивки остаётся выводимым из ключа.

### 1.3.1 Дешёвый поиск ключа
Сейчас сервер делает один X25519 на каждый ключ доступа для каждой датаграммы, которую не может отнести к сессии. В v6 в маскированный заголовок добавляется 4-байтовая ключевая метка, так что кандидат проверяется хешем, а не операцией на кривой. Цена: 4 байта в датаграмме рукопожатия. Открыто: хватает ли метки против того, кто шлёт мусор, чтобы тратить время сервера (см. вопросы ниже).

### 1.4 Повторное рукопожатие
Потерянный ответ сервера заставляет клиента отправить рукопожатие заново, и сервер отбрасывает повтор как реплей. В v6 сервер хранит свой ответ на время окна реплея и на повторное первое сообщение отвечает тем же ответом, не создавая вторую сессию. Это поверхность для зондирования (у атакующего с перехваченным первым сообщением ответ приходит снова), но ответ зашифрован на ключ, которого у него нет, так что ничего он не даёт.

### 1.5 Версия
`PROTOCOL_VERSION` становится 6 и, как в v5, входит в IKM, а на провод не попадает. Переходный сервер на датаграмме, которую не может отнести к сессии, пробует сначала v6, потом v5.

## 2. Уровень сессии
У каждого пункта есть проблема в 0.4.x и направление; подробности — на странице [v6-session-design.md](v6-session-design.md), которая идёт раньше кода.

| Проблема | Направление |
|---|---|
| Один потерянный кадр останавливает все потоки (одна последовательность на сессию). | Номера последовательности по потокам (`stream_seq`); заголовок растёт с 12 до 16 байт. |
| Поток сбрасывается, когда на медленный сайт ждут больше 32 МБ. | Управление потоком по каждому потоку, согласованное в 0.4.7, становится обязательным; сброса нет. |
| FIN приложения закрывает весь поток, и ответ после него теряется. | Половинное закрытие TCP отдельным сообщением. |
| Повторно использованный `u16` идентификатор потока может закрыться устаревшим Close. | Номер поколения в идентификаторе потока; у Close, Ack и Nack своё пространство nonce, чтобы ранний Close не обгонял данные. |
| Клиент узнаёт, что сервер его отбросил, лишь после примерно 10 с тишины. | Аутентифицированный Close сессии с причиной; он же несёт ошибки вроде отклонённого ключа. |
| Миграция угадывает по наибольшему nonce и перебирает сессии. | Идентификатор соединения, как в QUIC; сессия находится по нему. |
| Около 300 Мбит/с на сервер: один цикл, один системный вызов на датаграмму. | Шардирование по сессиям и GSO/`sendmmsg`; сначала замер в wirelab. |

## 3. Выкатка
- 0.5.0-beta.1: провод v6, переходный режим включён по умолчанию. Приложения и `ostp` создают профили v6; старые профили продолжают работать.
- Подписки объявляют минимальную версию клиента, чтобы приложение могло сказать «обновитесь».
- 0.6: переходный режим убирается.

## 4. Не в этом шаге
Носители (сначала WebSocket, затем QUIC/HTTP3, WebRTC, ICMP), DNS-политика сервера и kill switch на файрволе для Windows получат свои страницы. Рукопожатие они не меняют.

## 5. Как проверяется
- Чистая логика и векторы RFC в модульных тестах; тестов, которые лишь считают вызовы, нет.
- Сквозная проверка в wirelab: v6 против v6, клиент 0.4.5 против переходного сервера, пресет ТСПУ, потери и перестановки.
- Клиент 0.5.0 против сервера v5 должен завершаться понятным сообщением, а не тайм-аутом.

## Открытые вопросы
1. Хватает ли 4-байтовой метки, или для дешёвого поиска нужен индекс по первым байтам потока на каждый ключ?
2. Где живёт ключ сервера, если на одном сервере несколько доменов: один ключ на сервер (предлагается) или на каждый приёмник?
3. Нужен ли при смене ключа сервера переходный период, когда сервер отвечает обоими ключами?
